# ADR-0002: pyproject.toml is the source of truth for the version

**Status:** Accepted

**Date:** 2026-09-08

## Context

For most of its life `release` wrote a second copy of the version. After bumping
`pyproject.toml` it rendered a `VERSION_TEMPLATE` into `src/<package>/version.py`
so the released package could expose `__version__` at runtime, and committed
both. `057c0e7` extended this to projects with no `src` directory, since web
sites are laid out flat.

Two copies of a fact drift, and both did. The tool's *own* `version.py` was a
hand-maintained literal, and by the time anyone looked it claimed `0.5.0rc13`
while `pyproject.toml` said `0.5.1`. `release --version` was reporting a version
that had not existed for several releases.

The generated file was also the only reason `release` needed to know a project's
layout at all — where `src` was, what the package was called, whether the
distribution name needed its hyphens turning into underscores.

## Decision

`pyproject.toml` is the single *source* of truth for the version. `release`
writes no `version.py` into the projects it releases (`a7269e1`), and the tool's
own `__version__` is read from installed distribution metadata in
`src/release/version.py`:

```python
__version__ = version("release")
```

with a `PackageNotFoundError` fallback for a source tree that was never
installed. Nothing is hand-maintained, and nothing can drift.

One derived copy remains and is deliberate: `uv.lock` records the project's own
version too. It is generated by `uv lock`, never edited, and committed alongside
`pyproject.toml` in the same release commit — which is why both paths are
staged.

## Consequences

A project that wants `mypackage.__version__` at runtime must read its own
metadata, exactly as `release` now does. That is three lines and it is correct;
it is nevertheless a small thing the tool used to do for you and no longer does.

Metadata is written at install time, so an editable install reports the version
it was installed at until it is reinstalled. `uv run` re-syncs and therefore
tells the truth; a `uv tool install --editable` does not, and will lag after a
bump. It is cosmetic, and it is the price of not maintaining a literal.

Dropping the generated file also removed the tool's only interest in project
layout — `src_dir` and `mod_name` went with it — which is why the version bump
is now layout-agnostic while the *git* operations are not
([ADR-0014](0014-one-project-per-repository.md)).

## Alternatives considered

**Keep writing `version.py`.** It is convenient, and it is the reason the
divergence happened. Any scheme with two copies needs a mechanism to keep them
equal; the mechanism was "the tool rewrites one of them at release time", which
worked right up until a version was set by any other route.

**Dynamic versioning with `hatch-vcs`.** Derive the version from git at build
time and stop storing it anywhere. It is the tidier answer and it would also
have solved the snapshot problem in
[ADR-0010](0010-snapshots-are-local-versions.md). It was rejected as too large a
blast radius for the gain: it changes how *every* build resolves its version,
including builds that have nothing to do with releasing.
